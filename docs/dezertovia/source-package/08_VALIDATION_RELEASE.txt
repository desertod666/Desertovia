Проверки, данные и будущий выпуск

Что выполнено при подготовке пакета

Прочитаны закреплённые исходники игры и батюшки, их CI и тестовые файлы.
Сверены существующие пути и символы. Проверены связи JSON-задач, решений и
сценариев приёмки. Новые игровые тесты, нагрузка и настоящий сервер в этом
поручении не запускались. Пакет не содержит результата нового CI для 1.0.

Пирамида проверок

1. Доменные сценарии на фиксированных часах и воспроизводимой случайности:
   деньги/предметы/стоимость, отдых, бой, сценарии и разрешения.
2. API/PostgreSQL: реальные транзакции, advisory lock, два конкурирующих клиента,
   сбой до/после commit, старый requestId с изменённым содержимым, повтор worker.
3. Bot/SQLite: атомарное списание/начисление, повтор платёжного события, рестарт,
   отложенная привязка, expiry/grace и конфликт статусов. Внешние API подделаны.
4. Browser: полный пользовательский путь, reconnect/две вкладки, недоступная
   кнопка и причина, касания и прокрутка, реальные сетевые задержки в тестовой среде.
5. Длительные экономические/сценарные симуляции с явными начальными условиями.
   Отдельно наблюдаются концентрация богатства, цена корзины, доходы новичков,
   доля госработ и совокупный эффект premium. Не объявлять измерение балансом.
6. Нагрузка и реальные устройства: RTT, server work/lock/save/send, размер и
   частота обновлений, клиентская плавность, CPU/память всего хоста и сервисов.
7. Репетиция миграции/восстановления на синтетической либо явно обезличенной копии.

Команды, существующие в изученном game CI

Из корня game, в подготовленном окружении с .NET SDK из global.json:
dotnet restore Desertod.slnx
dotnet build Desertod.slnx -c Release --no-restore -v:q
dotnet test Desertod.slnx -c Release --no-build --logger trx --results-directory TestResults

Из web (Node24 в существующем CI):
npm ci
npm run lint
npm run test:unit
npm run build
npx playwright install --with-deps chromium
npm run test:e2e

Browser CI выполняет две части: npm run test:e2e -- --shard=1/2 и --shard=2/2.
Обе обязательны в соответствующем финальном CI. В текущей конфигурации
Desktop Chrome и Pixel7, а не полный WebKit/iOS. Переименовать тест в iPhone
недостаточно: для Safari нужны отдельные проверки движка и настоящего устройства.
Docker image build тоже часть текущего CI, а не доказательство установки.

Команды, существующие в изученном bot CI

Проверять .github/workflows/server.yml. В чистом подготовленном окружении:
npm ci --ignore-scripts --no-audit --no-fund --prefix town-client
npm run build --prefix town-client
git diff --exit-code -- assets/town/client.js assets/town/terrain.json
pip install -r requirements.txt
node tests/runner_engine.cjs
node tests/runner_balance.cjs
node --test youtube-reader/normalize.test.mjs
python -m tests.runner_physics_parity
python -m unittest discover -s . -p 'test_*.py' -v

Окружение CI включает Python3.12, Node24, audio tools. Эти команды указаны как
факт существующего pipeline, не как обязательство повторять весь набор после
каждой правки текста. Для изменения сначала подходящие узкие проверки,
затем необходимые интеграционные/регрессионные проверки и итоговый CI.

Опасные различия

Bot workflow при push main после тестов запускает server job с deploy по
умолчанию. Даже merge только документации нельзя считать автоматически
безвыкладочным действием. Не менять main ради этого пакета и не запускать
старый deploy с устаревшими runtime pins. Использовать актуальный reviewed процесс.

tests/Desertod.LoadTests — отдельный NBomber-генератор Development-профилей и
деревень. Это не xUnit-тест и не безопасная health-проверка рабочего мира.
Не направлять его на production. Не обходить аутентификацию ради нагрузки.

Целевые показатели

Конкурентный онлайн, число активных рейдов, минимальные устройства, p95/p99
задержки, допустимый трафик, FPS и бюджет модели пока не утверждены. Задача
T004 измеряет базу; решение D114 задаёт целевую нагрузку и допустимые регрессии.
Не вставлять собственное число в README и не выдавать его за решение владельца.
Наличие CPU22% в одном старом замере не доказывает ёмкость всего проекта 1.0.

Безопасность тестового окружения

Отдельные БД, домен, пользователи и каналы. Внешние Telegram/YouTube/Stars/Gemini
подделаны либо явно тестовые. Никаких личных данных, секретов или реальных
снимков пользователей в публичных артефактах. Не использовать производственные
учётные записи, ранение/предметы/платежи для демонстрации. Изоляция адреса не
достаточна, если тестовый сервер всё ещё отправляет в настоящий Telegram.

Репетиция изменения данных

До миграции зафиксировать профили/привязки, навыки, вещи и их размещение,
строительные состояния и номера, ранения, активные бои/данжи, деньги с резервами,
обязательства и receipts. Проверить, что последовательность миграции повторно
не выдаёт монеты, не меняет курс и не теряет CostBasis.
Старые EF миграции не редактируются; добавляются новые совместимые изменения.

Изменение labels не обязано менять хранилище. При переносе source-of-truth
нужны точка переключения, запрет двойной записи и сверка до/после. Исторические
счета не конвертировать до выбора курса/округления/TEST_CANDLE-политики.

Будущая установка

Нужны актуальные разрешение и процесс из приватных AGENTS/release guide,
точные проверенные SHA/CI и свежая база фактических файлов/сервисов. Не считать
основой нынешний main автоматически и не стирать изменения коллег.
Фактические backups, проверка восстановления, preflight → установка → отдельный
послерелизный check. Runtime версии игры и батюшки могут различаться по схеме
релизов; их нельзя насильно уравнять одним номером.

Откат

Для каждого флага описать: что прекращается, что доисполняется и какие данные
остаются. Принятый заказ должен либо закончиться, либо иметь корректный возврат;
выключение premium/директора не удаляет предметы и не отменяет обещания тайно.
При новом формате активных боёв/JSON старый бинарник может быть несовместим.
Нельзя автоматически залить старую БД поверх нового прогресса. При невозможности
безопасного отката остановить опасные новые действия, сохранить данные и разобрать.
