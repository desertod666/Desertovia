# Пошаговый план: адаптация, а не замена инженерии

Каждый этап — небольшой проверяемый PR с DZ-ID, схемой данных и сохранёнными
контрактами. Не начинать следующие крупные механики только потому, что их идея
есть в VIEWER_BACKLOG. Изменение баланса и изменение архитектуры — разные решения.

## 0. Восстановить контекст и исходные версии

Читать AGENTS → README → DECISIONS → нужные строки матрицы → реальные функции.
Проверить HEAD своей ветки/авторской основы/TG-bots источника. Изменённый исходник
не считать прежним только потому, что путь тот же. Сверить актуальную .NET/Node
версию и команды из README автора. Никаких рабочих ключей, БД и действий live.

Результат: перечень имеющихся capability, baseline SHA и неясностей. При изменении
основы сначала обновить матрицу, не применять старые patches вслепую.

## 1. Проверить и сохранить инженерный baseline

Отдельно запустить Domain tests, web build/lint и существующие e2e на локальном
изолированном окружении. Если нужны Docker, применять инструкции окружения.
Записать ошибки, существовавшие до адаптации, отдельно от новых. Проверить
startup migrations, shutdown settlement, cookie auth, SignalR и worker offline.

Не менять стек, ORM, rendering, routing, локализацию, карту и deployment-toolchain
ради удобства переноса Python-кода. Существующую архитектуру описать на схеме:

```
React/PixiJS → auth + HTTP intent → GameService/WorkContext → Domain rules
                                      ↓                     ↓
                              EF/PostgreSQL ← validated state/receipt
                                      ↓
                    settlement worker + notifier/outbox → SignalR/notifications
                                      ↕
                           узкий доверенный bridge батюшки
```

Результат: повторяемый старт/проверки и baseline поведения. Не объявлять безопасность
доказанной только потому, что запущены Domain unit tests.

## 2. Принять минимальную конфигурацию Дезертовии

Основной slug/OwnerAccount нашей Дезертовии, согласованные роли/tasks/проекты/экономика;
остальные существующие миры и возможности автора сохраняются.
Если авторские дефолты используются другими режимами, сделать компактный profile
в существующем WorkContext/options/catalog, не универсальный DSL/второй RulesEngine.
Не выключать полезные независимые функции автора без конкретного конфликта.

Все существующие функции автора сохраняются по D-013. Настроить разделение
миров/прав/запасов и согласовать готовые боевые сценарии с нашим хозяйством,
не выключая создание миров, роли, набеги или данжи.

Результат: основная Дезертовия и сохранённые режимы автора, понятная конфигурация и отсутствие
неожиданных новых способов добычи/зарплаты. DZ-01, 03, 34.

## 3. Связать пользователей и роли с батюшкой

Использовать AccountService/ExternalLogin и имеющийся Telegram verifier.
Сопоставление только provider numeric ID, не ник/отображаемое имя. Добавить
проверяемый MiniApp/login-ticket flow и срок/защиту повторов; bot token не на клиенте.
Узкий bridge проверяет игровой доступ и owner/assistant команды. .NET остаётся
владельцем игрового состояния, старый bot TownEngine больше не параллельно пишет его.

До публичного теста проверить принадлежность SignalR группы и повторную проверку
ограничений на команды. Изучить CSRF/origin/cookie/connection auth по реальному
контракту, не отключать защите ограничения ради iframe/MiniApp.

Результат: две попытки входа не создают двух персонажей; поддельный owner/ticket
не действует; чужое состояние недоступно для изменения прямым API. DZ-02, 18, 25.

## 4. Настроить поручения и энергию

Через TaskDefinition/GameCatalog/Energy/SkillRules задать наши базовые времена,
выходы и условия. Не переписывать CycleEngine целиком: использовать его Start,
Settle и Begin. Добавляемое время пути согласовать с существующим общим бюджетом.
Решить ограниченные старые бонусы и несовместимые stat gates из DECISIONS.

При принятии сохранить immutable существенные условия: task/site/deposit,
source/destination/inputs/output, duration/energy, reward, policy-version и receipt.
Проверить запас, роль, берег, состояние здания, напарника/места до списаний.

Результат: наш медленный темп и совместная игра; старые обещанные результаты
не теряются после настройки каталога; no tired exploit. DZ-03–05, 07, 14–15.

## 5. Добавить одну следующую команду

Использовать Citizen lifecycle, GameService и имеющийся settlement worker.
Не заменять worker очередями Redis и не делать новый cron только для одного next.
NextAction UI остаётся индикатором; рядом минимально добавить один queue state.

После завершения текущего: эффект + зарплата + next validation + start/pause
в согласованной транзакции. Освободить место при запуске next; невозможная команда
хранит объяснение, не запускается каждый heartbeat бесконечно. Не менять picker
на каждом snapshot, использовать stable React keys и отдельный draft.

Результат: race queue/start/poll/restart не дублирует job/награду, выбранный участок
не меняется. Связанные тесты текущего CycleEngine тоже проходят. DZ-05–06, 27.

## 6. Добавить конечные участки и разделение собственности

Расширить Forest/WorkSpots/WorldMap и StorageRules, сохранив геометрию/коллизии.
Участок имеет capacity, amount, regen rate и updatedAt. Не считать каждый
декоративный камень бесконечным серверным источником.

Сначала central ownership/funding checks для take/reserve/deliver/build/trade,
затем расширить stocks/properties. По всем путям снаружи нельзя тратить общий
запас. Определить судьбу несмещённого груза на границе; не вводить автоконвертацию
личного в общий при перерисовке/выходе. Груз и склад сохраняют сумму материала.

Результат: истощение/приток/разные участки работают после часов/суток/перезапуска,
обход через crafted request/queued courier невозможен. DZ-08–10, 16.

## 7. Адаптировать стройки и производства

Сохранить Projects/ConstructionSite/ConstructionRules и способы планирования.
Настроить зависимые открытия, независимые стройместа, остаток работы/резервы.
Добавить levels/condition/preparation/maintenance в существующие структуры.
Не тащить Python-проектные координаты в новую проекцию без spatial mapping.

Через существующий каталог расширить ресурсы и рецепты. Проверить реальное
назначение Food/Gold, не назвать ресурс Gold кошельком. Сначала повторить наши
подтверждённые цепочки, затем отдельным решением менять хлеб на муку.

Результат: мост/забор параллельны, после моста есть реальные задачи; мастер
изготавливает реальные товары; состояние не падает ниже мирного минимума.
DZ-11–13. Обязательный надзор инженера не становится несогласованной новой ролью.

## 8. Добавить дома, помощников и торговлю

Расширить blueprint/owner APIs и EF, не заменить GameService старым realm.py.
House/site owner, finance scope, заявки и полномочия оформляются сервером.
Через бот назначаются помощники, через наш API они готовят предложения;
одобрение выполняет только царь и ровно один раз.

Рынок передаёт существующие товары. Два покупателя одного лота и отмена/покупка
одновременно должны давать один исход. У продавца товар резервируется, деньги
и ownership переходят атомарно, возврат защищён отдельным receipt.

Результат: social/private funding, housing/refund, бывший assistant, outsider
и торговый replay проверены сценариями. DZ-16–19.

## 9. Дезкоины, учёт и ограниченный обмен

Wallet/ledger/test candle wallet/receipt добавить как EF extensions.
Номинал×10 применяется к импорту старого 0.4.2, а не к авторскому Gold или уже
переведённому миру. Импорт с версии 0.4.3 нельзя умножать снова.

Сохранить зарплаты/цены/лоты/возвраты и отдельный материал scope. Ввести cost basis
known/unknown, журнал изготовления/расхода, прибыль не оборот. Обмен с replay key,
5/сутки в real-time zone, не hourly game-day reset. Никаких записей в основной
кошелёк батюшки, обратного обмена или реального донатного баланса.

Результат: ledger reconciliation, двойной клик/worker race/сутки/возврат/остаток
квоты/импорт повторно проверены. DZ-20–23; tax preview не списывает.

## 10. Чат, бухгалтер и уведомления через существующие события

SignalR/React hooks обслуживают существующий чат, layout0/¼/full сохраняет
историю/draft/feed и одну подписку; отправка валидируется и ограничивается,
не доверяет имя/роль/body HTML. Стикеры проходят allowlist без произвольной SSRF.
Батюшка получает ограниченный контекст, отвечает по паузам; не выдаёт права/деньги.

Owner report считается точным кодом; AI получает агрегаты и возвращает совет.
Уведомления job-complete доставляются после commit и отдельно от выплат.
Переподключение не отправляет повторную зарплату или публичные тестовые сообщения.

Результат: integration contracts, permission and AI budget checks, реальные
телефоны/opt-in проверяются отдельным этапом. DZ-23–25, 28.

## 11. Минимальные клиентские поправки

Сохранить GamePage/GameMenu, CreateCharacterForm, i18n и Pixi VillageWorld автора.
Не рисовать новые ресурсы, не импортировать старый shell.js/main.ts/CanvasRenderer.
Чат адаптировать по отдельному явному запросу D-014 в существующем React UI.
Только необходимые controls/DTO fields для роли/next queue/ownership/market/
коротких ошибок; drafts не размонтируются при потоковых updates.

Присутствие: online ИЛИ выполняет работу. Показывать имеющееся движение и груз
на пути; любая визуальная скорость не сокращает серверную работу. Не прятать
активный job при уходе пользователя; offline idle уходит только с карты.

Результат: narrow phone, Android picker, клавиатура, PC, reload/reconnect и drag
не отправляют случайные команды. DZ-26–27, 35. Новый художественный блок остаётся PAUSED.

## 12. Полная проверка сценариев, а не буквального копирования функций

Использовать сохранённые Domain tests основы + новые профильные tests наших правил.
Старые Python tests переводятся как сценарии Given/When/Then, не как зависимость
нового API от Python. Meaningful DB integration и browser tests для конкуренции,
identity, сохранности и касаний. Не заменять реальные устройства mock-проверкой.

Минимум сценариев:

1. Новичок входит Telegram, выбирает доступную роль, выполняет работу с напарником.
2. Второй браузер/повтор запроса не создаёт двойной job; worker и API завершают один раз.
3. Следующий заказ сохраняет deposit/site, запускается либо объяснимо останавливается.
4. Истощение/12ч/новый участок/полный склад сохраняют обещанные результаты.
5. Внешний участок не берёт treasury в том числе через queued craft/courier/market.
6. Две сделки/одобрения/возврата одновременно не дублируют результат.
7. Профессия/опыт/дом/средства сохраняются при выходе/reload/рестарте.
8. Exchange replay/day boundary/DST/import×10 не дают повторный перевод и потери.
9. Нет основной свечной выплаты, налогового списания и AI mutation.
10. Старый интерфейс автора работает, активный офлайн виден, неактивный скрыт.
11. Снятые права/ограничение проверены на HTTP и SignalR, не только в кнопках.
12. Порядок Domain/EF/notifier сохраняет ожидаемое состояние при rollback/retry.

Результат: сопоставленные DZ-ID и фактические checks в progress.json.

## 13. Подготовить перенос данных или изолированный новый тестовый мир

Только на защищённых локальных копиях: источник SQLite 0.4.2/0.4.3 явно выбран,
schema version проверена; экспорт минимальных game data без sessions/bot secrets/
raw feedback/основного кошелька; Telegram-ID mapping и resource/project mapping.
Dry-run PostgreSQL import даёт отчёт totals/balances/ownership/jobs/queue/condition.
Проверить повторный запуск и rollback. Реальные данные не идут в git или CI artifacts.

Перед конкретным переключением определить, как закончить старые jobs либо перенести
их immutable условия, как остановить старый writer, доставить уведомления и сохранить
UID mapping. Не запускать одновременно два authoritative engine на тех же пользователях.

Результат: dry-run parity и reviewable switch plan. Новый тестовый мир — только
если владелец отдельно выбрал сброс, не из старого разрешения на прошлый тест.

## 14. Проверить выкладку и только затем переключать

Репозиторий пользователя — release authority; код автора поступает reviewed PR.
Проверить tracked files/history на секреты, зависимости, установочные скрипты,
Actions/Docker, production auth/no demo bots/dev login и права процесса.
Секреты server-only, внешние patches не получают deployment credential.

Изолированное окружение отдельно от текущего бота/сайта/других служб. Не занимать
их порты 80/443 и не запускать Caddy docker-stack поверх existing ingress вслепую.
ARM64/.NET10/resources/migrations/backup-health/HTTP/SignalR проверяются фактически.
Docker files автора сохраняем, адаптируя параметры запуска/порты к инфраструктуре.

Для rollback после новых записей недостаточно просто включить прежний writer:
остановить команды, reconcile записанные jobs/деньги, выбрать проверенный restore/
transfer plan и только потом переключить. Основные свечи всегда отдельно.

Результат: готовые проверенные файлы/миграции/checks и конкретный план выпуска.
Не выполнять deploy/reset в текущем документальном поручении.

## 15. Будущие механики отдельно

Новые отсутствующие идеи — замок/расширения, баня, дополнительные рецепты/качество,
больница/тюрьма, текстовый режим данжей и катаклизмы — идут отдельными decisions.
Готовые Tavern/Raids/Dungeon/классы автора уже сохраняются и адаптируются,
их не переносить в недоступное «будущее».
Сохранять их в backlog; включать только выбранный владельцем следующий этап,
через existing Domain/Projects/Quests/Storage/APIs. Не обосновывать полную смену
движка желанием добавить редкость предметов или ещё один квест.

## Универсальный метод адаптации другой игры

1. Составить inventory её engine/services/data/UI/auth/tests, зафиксировать SHA.
2. Разделить требования на совпадает / настройка / расширение / конфликт /
   отсутствует / отложено. Определить authoritative writer каждой сущности.
3. Найти эквивалентные точки Start/Settle/Reserve/Save/Publish; сделать mapping
   наших терминов к её понятиям. Не считать совпадение названия совпадением смысла.
4. Сначала менять профиль/каталог/числа; затем domain guards; затем данные;
   затем узкие интеграции. Adapter на границе предпочтительнее замены сервиса,
   но он не должен скрывать второй расчёт денег или результата.
5. Если возможности нет, добавить модуль в существующем extension mechanism,
   не перевести весь проект на привычный стек. Любая замена подсистемы требует
   объяснить, почему расширение невозможно, и отдельно выбрать её с владельцем.
6. Проверять поведение общими сценариями и invariant totals. UI использует
   подтвердившуюся существующую механику, не муляж наших старых API.
7. Сохранять feature ID → source → patch → migration → test → release в памяти;
   завершить небольшой вертикальный сценарий перед переносом следующего пакета.

Эта схема универсальна как метод работы. Она не обещает, что любые два движка
совместимы без изменений: сохраняются работающие инженерные решения выбранной
основы, а несовместимые правила обсуждаются и исправляются явно.
