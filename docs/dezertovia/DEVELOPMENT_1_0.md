## API-тесты без Docker Desktop

По умолчанию factory сохраняет прежний Testcontainers-путь CI. Для Windows
можно явно задать `DESERTOD_TEST_POSTGRES` с доступом к выделенному loopback
кластеру. Factory создаёт БД `desertod_test_<guid>` и после завершения удаляет
только её. Имя БД из входной строки никогда не используется как тестовый мир.
Нелокальный адрес отвергается. Migration-тесты, самостоятельно создающие
PostgreSqlContainer, по-прежнему требуют Docker и проверяются в CI.

```powershell
$env:DESERTOD_TEST_POSTGRES='Host=127.0.0.1;Port=55432;Username=desertovia_dev;Password=desertovia_dev_only'
..\tools\dotnet\dotnet.exe test tests/Desertod.Api.Tests -c Release --filter FullyQualifiedName~KingdomEconomyApiTests
```

Эта переменная предназначена исключительно для синтетического кластера.
Существующий CI игры строит .NET/клиент/Docker и выполняет обе browser-части,
без установки на сервер. Bot main может запускать deployment, поэтому первый
этап не меняет бот и его main. Проверки и точные результаты —
`IMPLEMENTATION_PROGRESS_1_0.json`; отсутствие проверенного кейса не означает PASS.

## Транзакционная основа PKG-T011

Помимо HTTP-повторов проверены два независимо созданных GameService: у каждого
свой in-process VillageLocks, общий только PostgreSQL. Одновременный одинаковый
requestId создаёт одну покупку/receipt; изменённый payload отклоняется. Проверены
кошелёк+казна, общий/личный товар и cost basis. Будущие госзаказы/налог проверяются
после их реализации; этот кейс не объявляет новые команды готовыми.

## Работа напарника PR76 и компактный интерфейс

По отдельному поручению владельца интегрирован `b617f8d` из PR76, с сохранением
истории (`4c04f69`). Ветку main и внешний PR этим объединением не закрывали.
Топоры/кирки повышают выход за прежнее время, расходуют одно применение и
сохраняют смешанный износ в руках/общем складе. Метаданные прочности входят
также в проекцию личных складов. Count-only торговый инвентарь проводит только
целые инструменты: покупка изношенного предмета не должна превращать его в новый.
Личное использование/торговля изношенным инструментом требует дальнейшего
контракта предметов; это ограничение не скрыто миграцией в обычное количество.

JSON-модель содержит новую прочность; миграция ToolDurability не меняет SQL-колонки.
Проверять старый JSON без поля, прежние предметы/заточку/прогресс, смешанные
прочности после повторного чтения БД и выбор точного stack по API.

Компактная оболочка: `INTERFACE_COMPACTNESS_1_0.md`. Кошелёк и восстановление
используют существующий Hint; каталог принимаемых складом ресурсов тоже открывается
по нажатию, чтобы восемь новых видов инструментов не раздували телефонную карточку.
Результаты компонентных fixtures не заменяют проверку физического телефона.
